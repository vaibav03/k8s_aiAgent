KubeAI: what it was, what it is now

The Kubernetes autoscaling and incident agent was rebuilt end to end: new data, models, serving and agent. Branch ml-service-upgrade on vaibav03/k8s_aiAgent.

In one line: the old system guessed from one pod's memory. The new one reads all four signal groups (compute, memory, traffic, request quality). It works out why a service is hurting, adds pods only when more pods will actually help, and otherwise fixes the cause.

Why it couldn't work
  • The label (status != Running) marked pods that had already crashed, so the model learned "crashed" rather than "about to crash".
  • LightGBM was scored on its own training data. The LSTM was 9× worse than just repeating the last value.
  • The agent's models didn't match the dataset. Memory was scaled one way in training and another way at serving.
  • Requests, latency and errors were never used, so the system could not decide when to scale.
  • A Google API key was committed in git history, so it must be rotated.

Decision states

The engine picks one state each tick.

healthy · scale_up · scale_down · memory_leak · dependency_latency · error_fault · noisy_pod · bad_deploy · crashloop · pod_restart

Safety rails
  • No scaling on faults that more pods can't fix
  • At most 1 restart per 5 min, and none while the deployment is under-ready
  • Never fights an existing HPA
  • kubectl is built by the agent itself via execFile; the LLM only fills an allowlist
  • Stale or missing telemetry freezes scale-down

Decision engine (deployment level)

PieceChoiceHeld-out result
State classifierFault rules + LightGBM load head (hybrid)macro-F1 0.844 (blind 0.803) vs HPA rule 0.139
CapacityLogistic P(SLO breach) on CPU utilisationAUC 0.967; recall 0.94 at 2.3% false alarms (HPA-70%: 25.6% false alarms)

Fault replayFault gateAdds pods on 0% of held-out fault decisions
Result against expectations: a forecast-driven scaler did not beat a tuned HPA at the same cost (held out: 2.17 vs 0.67 SLO-violation minutes). So forecasting is advisory only, and the shipped policy sizes reactively from learned capacity and adds the fault gate. The shipped default is HPA_GATED: HPA sizing (CPU 70%, 30 s scale-down) plus the fault gate. In replay it ties the HPA on load (0.67 vs 0.67 violation-min) and adds pods on 2.3% of fault decisions, against 16.5% for the HPA (0.50 vs 3.75 wasted pod-min).

Where the agent loses or is unproven
  • In 2 of 3 runs it read the spike overload as dependency_latency once (a false page).
  • After the leak restart, the memory_leak state blocked scale-up for about 60 s (the latch has since been shortened).
  • n = 1 per arm, one service on one node. A second seed failed because the API server overloaded.
